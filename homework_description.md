## Пункт 1: Добавление новой строки с новым бизнес-ключом
В файл source_customers.csv добавлен новый клиент:
```
id: 105
first_name: Alex
last_name: Johnson
email: a.johnson@newmail.com
```

### Что произошло с данными на всех этапах:

1. **Source (CSV файл)**:
   - Добавлена новая строка с уникальным id=105
   - Создан новый уникальный email (бизнес-ключ)

2. **Stage слой (stg_customers)**:
   - Сгенерирован новый customer_pk (хеш email a.johnson@newmail.com)
   - Добавлено поле RECORD_SOURCE = '!CSV_CUSTOMERS'
   - Добавлено поле EFFECTIVE_FROM = now()
   - Создан CUSTOMER_HASHDIFF на основе first_name, last_name и email
   - Все исходные поля перенесены без изменений

3. **Raw Vault**:
   - **Hub (hub_customer)**:
     - Добавлена новая запись с бизнес-ключом (email)
     - Сохранен сгенерированный customer_pk
     - Записаны load_date и record_source
   - **Satellite (sat_customer)**:
     - Создана новая запись с атрибутами клиента
     - Сохранены first_name = 'Alex', last_name = 'Johnson'
     - Записан CUSTOMER_HASHDIFF для отслеживания изменений
     - Установлены effective_from = now() и record_source = '!CSV_CUSTOMERS'

4. **Business Vault**:
   - **PIT таблица (customer_pit)**:
     - Добавлены записи для всех дат из as_of_date
     - Новый клиент отражается только в снимках после даты его добавления
     - История изменений начинается с момента добавления записи

### Важные особенности реализации:
1. Data Vault корректно обрабатывает новые записи через инкрементальные модели
2. Историчность обеспечивается через effective_from без явного effective_to
3. PIT таблица позволяет получить состояние данных на любой момент времени

## Пункт 2: Добавление строк с существующим бизнес-ключом
Изменены данные для существующей записи в source_customers.csv:
```
id: 104
Было:
first_name: Donald
last_name: Trump
email: d.trump3@usa.gov

Стало:
first_name: Donald Jr
last_name: Trump
email: d.trump3@usa.gov
```

### Что произошло с данными на всех этапах:

1. **Source (CSV файл)**:
   - В исходном файле изменены атрибуты для id=104
   - Бизнес-ключ (email) остался неизменным
   - Изменено только значение first_name

2. **Stage слой (stg_customers)**:
   - Сгенерирован новый CUSTOMER_HASHDIFF, т.к. изменились атрибуты
   - Customer_pk остался тем же (основан на неизменном email)
   - Новая запись получила новый effective_from

3. **Raw Vault**:
   - **Hub (hub_customer)**:
     - Не добавлено новых записей, т.к. бизнес-ключ не изменился
     - Существующая запись осталась без изменений
   - **Satellite (sat_customer)**:
     - Добавлена новая версия записи с измененными атрибутами
     - Старая версия сохранена с прежним effective_from (17:51:52)
     - Новая версия получила новый effective_from (18:00:11)
     - История изменений корректно сохранена

4. **Business Vault**:
   - **PIT таблица (customer_pit)**:
     - В снэпшотах до момента изменения отражается старая версия
     - В снэпшотах после изменения отражается новая версия
     - Обеспечена полная историчность изменений

### Важные наблюдения по обработке изменений:
1. Хаб не изменяется при обновлении атрибутов (только бизнес-ключ важен для хаба)
2. Сателлит хранит обе версии записи с корректными временными метками
3. Механизм историчности Data Vault корректно обрабатывает изменение атрибутов без необходимости явного указания effective_to

## Пункт 3: Удаление строки из CSV файла
В файле source_customers.csv удалена запись клиента:
```
id: 99
first_name: Mary
last_name: Gray
email: mgray2q@constantcontact.com
```

### Что произошло с данными на всех этапах:

1. **Source (CSV файл)**:
   - Физически удалена строка с данными Mary Gray
   - Нумерация остальных строк осталась без изменений (id=99 больше не используется)

2. **Stage слой (stg_customers)**:
   - Запись полностью отсутствует в выгрузке
   - При следующем обновлении моделей эта запись больше не попадает в stage

3. **Raw Vault**:
   - **Hub (hub_customer)**:
     - Запись сохраняется в хабе (принцип историчности Data Vault)
     - Бизнес-ключ (email) остается в системе
   - **Satellite (sat_customer)**:
     - Последняя версия записи сохранена с effective_from = '2025-05-11 17:51:52'
     - История изменений полностью сохранена
     - Возможно отследить, когда запись была актуальна

4. **Business Vault**:
   - **PIT таблица (customer_pit)**:
     - Запись Mary Gray отображается в исторических снимках
     - Технические поля (sat_customer_ldts) показывают время последнего обновления
     - Можно получить состояние данных на любой момент времени

### Важные выводы по удалению данных в Data Vault:
1. Физическое удаление происходит только в источнике (CSV) и stage-слое
2. Raw Vault сохраняет все версии записей, даже удаленных
3. Через PIT таблицу можно восстановить состояние данных на любой момент времени
4. Обеспечивается полная историчность данных - мы всегда знаем:
   - Когда запись была добавлена (first effective_from)
   - Какие были изменения (версии в сателлите)
   - Когда запись стала неактуальной (последний effective_from)

## Пункт 4: Создание витрины по количеству заказов
Создана витрина order_by_week для анализа динамики заказов по неделям.

### Реализация:
1. **Создание витрины**:
   - Использована таблица sat_order как источник данных
   - Заказы сгруппированы по неделям используя DATE_TRUNC('week', order_date)
   - Добавлена группировка по статусу заказа
   - Рассчитан накопительный итог для каждого статуса

2. **Структура витрины**:
   - week_start: начало недели
   - status: статус заказа (completed, returned, return_pending)
   - order_count: количество заказов за неделю
   - cumulative_count: накопительный итог по количеству заказов

3. **Особенности реализации**:
   - Витрина материализована как таблица для быстрого доступа
   - Данные отсортированы по неделе и статусу
   - Возможен анализ трендов как по неделям, так и по статусам

### Результаты анализа:
- Видна еженедельная динамика заказов
- Можно отследить соотношение успешных и возвращенных заказов
- Накопительный итог позволяет видеть общий рост числа заказов

## Пункт 5: Создание витрины клиентов по количеству завершенных заказов
Создана витрина customers_by_completed_orders для анализа клиентов по количеству успешно завершенных заказов.

### Реализация:
1. **Создание витрины**:
   - Использованы таблицы sat_order, link_customer_order и sat_customer
   - Отфильтрованы только заказы со статусом 'completed'
   - Подсчитано количество завершенных заказов для каждого клиента
   - Результаты отсортированы по убыванию количества заказов

2. **Структура витрины**:
   - first_name, last_name: имя и фамилия клиента
   - email: email клиента (бизнес-ключ)
   - completed_orders_count: количество завершенных заказов

3. **Особенности реализации**:
   - Витрина материализована как таблица для быстрого доступа
   - Используется DISTINCT ON для получения актуальных данных клиентов
   - При одинаковом количестве заказов сортировка по email
   - Учтены клиенты без заказов (LEFT JOIN + COALESCE)

### Результаты анализа:
- Выявлены самые активные клиенты (топ-4 имеют по 3 завершенных заказа)
- Можно идентифицировать клиентов с наибольшей покупательской активностью
- Данные могут быть использованы для программ лояльности
